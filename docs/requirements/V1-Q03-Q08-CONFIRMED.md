## Changed vs baseline
- `V1-R01` + `V1-R08`: boot-before-login is now explicit. Desktop keyring access at boot MUST NOT be presumed. GUI must never gate service READY.
- `V1-R02`: pinned + controlled upgrades is confirmed policy; no automatic unreviewed download/apply.
- `V1-R04` + `V1-R06` + `V1-R09`: write tools require authenticated approval per exact proposed diff; model-issued approval is not authoritative. Project dual logbooks remain distinct from protected runtime operations audit.
- `V1-R05`: one aggregated endpoint is mandatory. Native tunnel multichannel != evidence of one unified MCP namespace unless shown by ChatGPT E2E.
- `V1-R07`: Ubuntu GUI/tray is REQUIRED for V1 release, while ChatGPT MCP Apps, rich per-server autogenerated forms, and Windows GUI remain staged/OPEN as applicable.
- `V1-R03` / `V1-R08`: E2E after gate; fake/local tests may be planned earlier, actual test process only under separate approval. Modern MCP 2026-07-28 does not use old initialize handshake; negotiate/test the version actually encountered.

## Conflicts, implications and open decisions
1. Q03A vs user-session keyring: system-boot service cannot depend on a locked user desktop keyring; boot-capable protected secret store and least-privileged identity must be designed and approved. Distinguish "starts immediately" from successful network readiness.
2. Q06A vs Q03A: GUI MUST at V1 release but MUST NOT run at early boot or be a service dependency. Wayland may offer tray menu instead of exact click-popup or anchored position; operator must approve required UX fallback before GUI ADR acceptance.
3. Q07A vs tunnel native channels: unified ChatGPT discovery/routing contract needs isolated proof; choose own router only if necessary. Protocol 2026-07-28 vs 2025-11-25 semantic bridging is nontrivial; unsupported capabilities fail closed.
4. Q05A vs remote ChatGPT approval: no model-created approval or plain `approved=true` field; approval must bind identity, privilege, immutable change digest, registry revision, expiration and single-use nonce, then revalidate on apply.
5. Q08A vs existing services: approval is only for planning; do not start, stop, restart, alter, replace or cut over any existing tunnel/proxy/service. Operator must separately authorize isolated credentials and E2E execution.
6. Windows parity vs V1 Ubuntu release: Windows target retained for future phase, not silently moved into Ubuntu V1 release blocker.

## Acceptance gates (all NOT RUN)
- G00 Requirements: these six choices confirmed; all other Q01..Q08 details remain OPEN as documented; ADRs only PROPOSED.
- G01 Boot/headless: cold boot with no user login/no DISPLAY; service reads authorized config/secret refs and responds locally; injected locked-user-keyring failure does not yield false READY; no existing-service changes.
- G02 Version control: verify pinned artifact against official provenance; reject mismatched digest and unapproved upgrades; rollback safe test binary.
- G03 Approval: propose has NO side effects; unauthorized/expired/replayed/altered/stale-revision apply DENIED and audited; approved exact diff applied at most once; rollback prior isolated registry snapshot.
- G04 Aggregation: ChatGPT one endpoint sees namespaced tools for two distinct fake MCPs and calls both through independent routes; collision/crash/malformed schema isolation; rollback isolated routing generation.
- G05 GUI/headless: manual tray/launcher/settings/status test on target GNOME Wayland; absent GUI, close and crash GUI leave service alive; fallback when direct click event unavailable; remove test GUI only.
- G06 E2E authority: verified target Platform org + ChatGPT workspace access, dedicated tunnel/profile, host-protected temporary credential, operator approval recorded before starting; after test revoke/rotate; legacy before/after unchanged.
- G07 Audit: verify CTMM documentation event in Git and Obsidian logs; later runtime audit independently tested without secret leakage. No PASS before evidence.
