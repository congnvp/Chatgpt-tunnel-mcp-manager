# CTMM Registry / Settings V1 — Contract Proposal
Status: PROPOSED ONLY (not an accepted ADR; no code/runtime change)
Event: CTMM-20261016-010 · Workstream: Registry/Settings · Scope: V1-R04/R06/R07/R08/R09, P05
Dependencies: D-ARCH-02 (service/IPC), D-ARCH-04 (MCP transport/proxy), D-ARCH-06 (security/secrets/audit). All OPEN.

## 1. Ownership and invariants
- Rust headless service owns authoritative desired Registry configuration and its revision. The GUI, CLI and ChatGPT management MCP are clients of the same policy-gated service boundary. No independent UI copy writes.
- Separate persisted `desired` from observed runtime health, process IDs, negotiated capabilities, last errors, and diagnostics. Desired `enabled=true` never means READY.
- Scope every managed server by a stable `server_id` and a `profile_id`; namespace/alias is mutable, identity is not. Use normalized case-insensitive aliases unique inside a profile, and explicit cross-profile exposure policy; final tool namespace mapping belongs to Proxy ADR.
- Built-in management MCP, tunnel, and proxy are system components, not user-editable imported external servers. Their status remains available locally if tunnel is offline.
- Changes require `expected_revision`, canonical validation, authorization, audit and atomic persistence; runtime activation/reconciliation is a separate observable step. Concurrency conflict does not overwrite another writer.
- Disabled servers have no startup side effects. A write proposal never changes state until server-side approval and apply gates succeed.

## 2. Proposed versioned desired-state model (illustrative JSON, not approved machine schema)
```json
{
  "schema_version": 1,
  "registry_revision": 12,
  "profiles": [
    {"profile_id": "isolated-lab", "display_name": "Isolated lab", "activation_policy": "manual"}
  ],
  "servers": [
    {
      "server_id": "srv-lab-echo",
      "profile_id": "isolated-lab",
      "alias": "echo",
      "display_name": "Echo MCP (test)",
      "enabled": false,
      "transport": {
        "kind": "stdio",
        "executable": "/opt/ctmm-test/bin/echo-mcp",
        "args": ["--mode", "safe"],
        "working_directory": "/opt/ctmm-test"
      },
      "secret_bindings": [
        {"target": "env", "name": "EXAMPLE_TOKEN", "secret_ref": "secret://ctmm/isolated-lab/echo-token"}
      ],
      "execution": {
        "startup_timeout_ms": 10000,
        "request_timeout_ms": 30000,
        "max_concurrent_requests": 4,
        "restart_policy": "on_failure"
      },
      "exposure": {"tools": true, "resources": false, "prompts": false}
    }
  ]
}
```
The sample URI is an inert logical identifier; never treat it as a credential, a file path or an instruction to create a secret. Values above are illustrative, not tested defaults.

## 3. Proposed type contract
| Object/field | Required | Rule |
|---|---|---|
| schema_version | yes | Strict supported integer/version, reject unknown major versions; explicit migrator before upgrade |
| registry_revision | yes | Monotonic CAS revision set by service; read-only for all clients |
| profiles[] | yes | Unique immutable ID, display name, owner/scope, activation policy; V1 no implicit inheritance |
| servers[].server_id | yes | Stable opaque local identity; generated by service, cannot change on edit/import |
| servers[].profile_id | yes | Must reference known profile, no implicit selection of privileged/default production profile |
| servers[].alias | yes | Unique normalized slug within namespace scope; collision and reserved-prefix rejection |
| servers[].enabled | yes | Desired boolean, default false on import |
| servers[].transport | yes | Discriminated union: stdio, streamable_http; legacy_sse only after compatibility gate |
| servers[].secret_bindings | no | Target/name plus opaque secret_ref; never plaintext; fail closed when missing |
| servers[].execution | yes | Bounded startup/request timeout, concurrency, restart/backoff constraints |
| servers[].exposure | yes | Explicit tools/resources/prompts allow/deny; no implicit privileged tools |
| observed status/capabilities | no | Separate read-only runtime snapshot, never authoritative config or exported desired state |

Transport variants: `stdio` uses absolute allowlisted executable, structured args array (NO shell interpolation), bounded working directory and selected environment binding. `streamable_http` uses validated HTTPS endpoint, explicit auth reference, redirect/TLS/loopback policy and protocol-capability checks. `legacy_sse` must be opt-in behind version matrix and cannot be silently substituted. Network restrictions and tool namespace policy require Proxy/Threat-model review; candidate endpoint restrictions include SSRF/private-address/metadata-service protection with explicit local exceptions only for isolated test profiles.

## 4. Field ownership and edit rights
| Field class | Read-only | Local-editable (authorized) | AI-proposed |
|---|---|---|---|
| Identity, revision, created/updated timestamps, provenance | yes | no | no |
| Observed health/errors, negotiated protocol version, process metadata | yes; sanitized | no | no |
| Alias, display name, desired enabled, bounded timeouts, exposure flags | no | yes | yes, never auto-apply |
| Executable/args, working directory, URL/transport, profile assignment | no | privileged local editor after validation | suggest only; elevated review |
| Secret references/bindings, operator approval policy, trust/allowed executable roots | redacted read | privileged local secret/config administrator | cannot read or set arbitrary references; may request manual binding |
| Actual secret values, approval tokens/nonces, runtime env bytes | never returned | provision only via host-controlled secure flow | forbidden |
| Built-in manager/proxy/tunnel authority and audit records | yes | dedicated system admin for policy only after ADR | never mutable via generic server editor |

`readOnlyHint`, `destructiveHint` and UI approval prompts are advisory metadata, NOT substitutes for server-side authorization.

## 5. Validation pipeline (deterministic before side effects)
1. Strict decode, size/depth/count bounds; reject unknown critical fields, duplicate JSON keys, noncanonical encodings and unsupported schema version.
2. Local schema/range checks and discriminated transport-specific required/excluded fields; stable immutable IDs and normalized aliases; reserved names/collisions.
3. Referential integrity: profile exists, binding targets unique, no dangling/duplicate `secret_ref` aliases; do not resolve or disclose secret values during proposal.
4. Security lint: reject plaintext secrets in env/header/argument fields, shell mode/injection, path traversal/symlink escape, executable outside allowed roots, untrusted URLs/redirects or unsafe local-network access according to policy. Do not claim heuristic secret scanning catches all leaks.
5. Policy checks: actor identity, profile scope, tool permissions, requested operation sensitivity, required local confirmation; deny unauthorized even if client omitted its identity/metadata.
6. Compatibility check against supported transport/protocol matrix; check executable existence and permissions only during local preflight, not during import; optional dry-run isolated connectivity with explicit opt-in.
7. Return structured diagnostics: `field_path`, `code`, `severity`, `safe_message`, optional remediation; exclude raw tokens, secret values, unchecked subprocess stderr, and sensitive paths from AI-facing errors.
Invalid input leaves registry/runtime unchanged.

## 6. Profiles and lifecycle
- A profile is an isolation/activation boundary, not merely a UI filter; service ownership, permissions, secret namespace, tunnel association and exposed servers require an explicit design ADR.
- V1 candidate: `isolated-lab` plus optional separate user profiles, each with unique IDs; no auto-activation of imported profiles.
- Server desired lifecycle: DRAFT -> VALIDATED -> APPROVED -> PERSISTED -> RECONCILING -> READY/DEGRADED/FAILED; these are operational workflow phases, not a substitute for Core's typed runtime status machine.
- Disabling revokes future routing immediately after policy-checked apply; in-flight requests follow bounded draining/cancellation policy from Proxy/Core ADR. Do not conflate disabled desired config with process termination success.
- Startup/enable success is measured by MCP initialize/tool contract evidence, not merely child process presence.

## 7. Secret storage and exposure
- Persist only opaque `secret_ref` identifiers; actual secret stored with restricted host secret provider after D-ARCH-06. No literal keys in Git, Obsidian, diagnostics, export or JSON fixtures.
- Environment variable names are allowed descriptors; environment variable *values* are injected only at supervised child launch from trusted store, never logged/exported. Avoid inheriting the entire manager environment.
- Secret provisioning/rotation/removal is a LOCAL privileged workflow; a model may request a missing binding but must not supply/store a credential through tools or UI form.
- Host adapters on Ubuntu/Windows remain OPEN (service context, headless unlock, machine-vs-user scope, OS APIs and secret lifecycle). Never assume desktop keyring accessible at boot.

## 8. Mutations, rollback and audit
- Read tools: `list_servers`, `get_server_config_redacted`, `validate_server_draft`, `get_registry_revision`, `export_registry_sanitized`.
- Two-stage control: `propose_server_change(change, expected_revision, idempotency_key)` returns immutable diff, risk tier and expiration; privileged operator approves through out-of-band/local authenticated boundary; `apply_approved_change(proposal_id, expected_revision)` rechecks authority, approval binding, expiration, revision and policy.
- Approval bound to actor, profile, exact canonical change digest and current revision; short-lived, single-use, revocable. ChatGPT tool execution alone never constitutes operator approval.
- Atomic persistence: validate -> durable snapshot/revision commit -> asynchronous reconcile -> verify observable outcome. On reconcile failure attempt an authorized safe restore of prior snapshot and recover the prior isolated server runtime. If restore fails, report DEGRADED plus manual-recovery instructions; never claim automatic success.
- Audit record (separate from paired project CTMM logbooks): UTC timestamp plus Asia/Bangkok presentation, operation_id, actor/role, auth decision, proposal/diff hash, old/new revision, target IDs, result/error_code, redacted evidence and rollback linkage. Append-only/tamper-evident design and retention remain ADR OPEN. Do not log secret or raw untrusted tool payloads.

## 9. Sanitized import/export
- Export versioned envelope with format version, compatible schema version, desired config only, profile/server descriptors, provenance and checksum for integrity detection (checksum is NOT authenticity proof).
- By default REMOVE secret values, secret reference identifiers, access tokens, auth headers, runtime environment, observed health/logs, absolute private filesystem roots if not explicitly consented, and any unresolved suspicious inline values. Replace with `secret_requirements` placeholders describing bindings to provision locally. State redaction warnings and non-round-trip limitations.
- Import is PREVIEW ONLY by default: bounded parser -> schema validation -> normalized diff -> duplicate/alias conflict review -> profile remapping -> executable/endpoint trust gate -> operator approval -> save as disabled, then separate explicit enable. Never execute downloaded config or overwrite local secret bindings.
- Unknown schema major, malicious archives/paths, duplicate IDs, stale revision, missing secrets and forbidden transport produce named safe errors. No auto-merge to production or auto-enable.
- Exact round-trip preservation may require a privileged local sealed-backup format with OS-specific secret lifecycle; explicitly OUT OF SCOPE for portable sanitized export.

## 10. ChatGPT MCP Apps UI proposal (OPTIONAL, AFTER headless tools)
- Portable MCP Apps view via `_meta.ui.resourceUri` and versioned `ui://ctmm/registry/v1`; iframe resource uses `text/html;profile=mcp-app` and standard `ui/*` bridge. Data tools remain usable without UI.
- Suggested tabs: server list/status, redacted server details, configuration draft editor, validation issues, side-by-side diff/permission explanation, approved change history. The UI never owns persisted Registry state.
- Data tools return typed structured results; a separate `render_registry_widget` attaches UI resource only when visual review is useful. UI invokes exactly the same permission-gated tools; no direct file/process writes from iframe.
- The UI may display approval pending and direct user to trusted local approval. Never assume clicking inside the iframe satisfies elevated server-side local approval. Content Security Policy must restrict network origins; render untrusted MCP descriptions as inert text.

## 11. Offline-first contract and negative test matrix (NOT RUN)
| ID | Scenario | Expected |
|---|---|---|
| RS-01 | Add valid disabled fake stdio server in isolated profile | Validate; persist new revision; no process launch |
| RS-02 | Duplicate alias, reserved manager alias, invalid server ID | Reject, no change |
| RS-03 | Unsupported transport or future schema major | Reject with versioned error |
| RS-04 | Shell-embedded command, unsafe exec path/symlink | Reject; no child execution |
| RS-05 | HTTP SSRF/redirect/metadata address; invalid TLS policy | Reject or require explicitly approved lab exception |
| RS-06 | Missing secret_ref or unbound secret | Fail closed; sanitized error; no reveal |
| RS-07 | Literal secret in imported env/header field | Reject and redact diagnostic |
| RS-08 | Portable export and re-import | No secret values/refs; staged disabled; rebinding required |
| RS-09 | Unauthorized AI apply without local approval | DENY, audited, revision unchanged |
| RS-10 | Expired/replayed/cross-profile approval | DENY, audited |
| RS-11 | Concurrent writers same expected_revision | One winner; stale writer conflict; no lost update |
| RS-12 | Duplicate idempotency key with identical/different payload | Safe identical retry; conflicting payload rejected |
| RS-13 | Persistence crash/power loss mid-write | Prior or new valid atomic revision; never partial file |
| RS-14 | Reconcile failure after valid write | Safe previous snapshot restore or DEGRADED with evidence |
| RS-15 | Disable during in-flight call | Bounded drain/cancel; routing deny new calls |
| RS-16 | No DISPLAY / GUI closed / tunnel offline | Local registry and diagnostics continue |
| RS-17 | Untrusted strings in labels/errors/widget | Escaped/inert; no script execution or credential leak |
| RS-18 | Profile reassignment or built-in manager modification by AI | Privilege denial; no critical-service changes |

Evidence gate: use fake secret store, fake process/clock, temporary isolated directories/profiles, unit/contract tests and fault injection; later headless cross-platform tests. No test here has been executed.

## 12. ADR candidates and tasks (not accepted)
- REG-ADR-A: data format/store (strict JSON vs TOML vs SQLite), revision/CAS, crash-safe commit/migration and backups. Prefer smallest transactional implementation supported by evidence, not preselect SQLite.
- REG-ADR-B: profile authority and secret store ownership (per-user vs machine service; Linux boot/unlock vs Windows service).
- REG-ADR-C: local UI/MCP auth, approval provider, actor identity and durable runtime operation journal.
- REG-ADR-D: import trust model, collision normalization, standard profile portability and secret rebinding.
- REG-ADR-E: enable/disable transactional semantics, live routing drain and recovery contract with Core/Proxy.
- Task RS-D01: agree fields/constraints/schema versions (dependency: P00 auth/transport baseline). Acceptance: reviewed schema + positive/negative fixtures; rollback: revise proposal.
- Task RS-D02: permission matrix + threat model + approval flow (dependency: D-ARCH-06). Acceptance: explicit allow/deny cases; rollback: deny all writes.
- Task RS-D03: import/export sanitizer/rollback contracts (dependency: RS-D01/D02). Acceptance: fake credential leak checks + fault injection design; rollback: disable import.
- Task RS-D04: optional MCP Apps render contract (dependency: stable tool schemas). Acceptance: works without UI; rollback: unregister UI resources only.
- Implementation P05 blocked until P00 architecture/security gates and P01–P04 headless/provider contracts provide evidence.
